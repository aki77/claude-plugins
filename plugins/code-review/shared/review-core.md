# review-core: pr-review / local-review 共通レビューパイプライン

**このファイルは単体スキルではない。** `pr-review` / `local-review` が、それぞれのモード別パラメータを確定させた上でこのファイルを読み込み、以下の手順（ステップ1〜7）を**一字一句そのとおりに実行する**ためのものである。呼び出し元は独自の追加・省略・解釈変更をしない。

本文中では、呼び出し元 SKILL.md が与えるモード別パラメータを**太字名**（例: **context引数**）で参照する。呼び出し元は自身のモード別パラメータ表で各太字名の値を確定させてから読み込むこと。

**エージェントへの前提（すべてのエージェントおよびサブエージェントに適用）:**
- すべてのツールは正常に動作する前提で利用すること。動作確認や試し打ちのための呼び出しは行わない。この前提はすべてのサブエージェントにも明示すること。
- ツールはタスク完了に必要な場合のみ呼び出す。すべてのツール呼び出しには明確な目的が必要。

以下の手順を厳密に実行してください:

1. `node ${CLAUDE_PLUGIN_ROOT}/scripts/collect-review-context.mjs <context引数>` を実行して、変更ファイルへのレビュー準備情報（レビュー対象フィルタ結果 + プロジェクトルール適用結果）を取得する（**context引数** はモード別パラメータ表を参照）。ルール（CLAUDE.md と `.claude/rules/`）および `.gitattributes`（後述の除外判定に使う）はローカル作業ツリーから読み込む。**スクリプトは結果を一時ファイルに書き出し、そのパスのみを標準出力に1行で返す。** このパスを変数に束ねて以降のステップで使い回し、必要な値は `jq` で取り出すこと（例: `CTX=$(node ${CLAUDE_PLUGIN_ROOT}/scripts/collect-review-context.mjs <context引数>)`）。JSON の形式は以下:
   - `source`: レビュー対象の種別。`"pr"`（PR の base...HEAD 差分）/ `"range"`（git range のコミット差分）/ `"staged"`（ステージ済み変更）。
   - `diffArgs`: 後続ステップで `git diff` に渡す引数の配列（全モード共通で存在）。PR / range モードでは `[<range>]`、staged モードでは `["--staged"]`。
   - `range`: 解決済みの git range（例: `abc123...HEAD`）。`source` が `"pr"` または `"range"` のときのみ存在する（staged モードでは存在しない）。
   - `changedFiles`: レビュー対象の変更ファイルパスの**文字列配列**（オブジェクトではない。例: `["a/b.ts", "c/d.rb"]`。下記フィルタで除外されたものは含まれない）。取り出すときは `.path` を付けず `jq -r '.changedFiles[]' "$CTX"` とすること。
   - `excludedFiles`: レビュー対象から**機械的に除外**した変更ファイル一覧。`changedFiles` と同型の**文字列配列**（生成物・ミニファイ・バイナリ、または `.gitattributes` の `linguist-generated=true`）。**具体的な除外条件はスクリプトが確定済みで、この配列が唯一の正**。SKILL 側で条件を再判定・列挙しないこと。
   - `excludeArgs`: 除外ファイルを diff から落とすための、コマンド別の**組み立て済み引数**。`excludeArgs.git` は `git diff` 用（`-- . ':(exclude)<path>' ...`）。除外ファイルが無ければ空配列。
   - `assignments`: エージェント1・2への担当割り当て（2要素の配列。`assignments[0]` がエージェント1用、`assignments[1]` がエージェント2用）。**`changedFiles`/`excludedFiles`（文字列配列）とは異なり**、各要素は `files` を持ち、`files` は `{ path, rules }` の**オブジェクト配列**。
     - `path`: 担当する変更ファイルのパス。
     - `rules`: そのファイルに適用されるルールファイルのパス一覧（適用される CLAUDE.md と `.claude/rules/` を区別なく列挙。親ディレクトリのCLAUDE.md・`paths` がそのファイルに一致する `.claude/rules/`・`paths` 未指定の全適用ルールがすべて含まれ、一致しないルールは含まれない）。スコープ判定はスクリプトが済ませているため、エージェントは `rules` をそのまま参照すればよい。
   - `assignments` は `excludedFiles` を除いた `changedFiles` のみを対象に組まれている（エージェント1・2は自動的に除外ファイルをスキップする）。適用ルールセットが同一のファイルが同一エージェントに寄せられ、かつ各エージェントが担当ファイルに不要なルールを読まずに済むよう、スクリプトが決定論的に振り分け済み。

   **diff 取得の統一則: 以降 diff を取得するすべての箇所では、`git diff $(jq -r '.diffArgs[]' "$CTX") $(jq -r '.excludeArgs.git[]' "$CTX")` を実行すること**（`diffArgs` が range / `--staged` を、`excludeArgs.git` がレビュー対象外ファイルの除外を担う。除外ファイルが無ければ後者は空になり従来と同じ）。これによりエージェント3・4・5 やサマリエージェントが読む diff からも生成物・バイナリが除かれる。全モードでこの1コマンドに統一されているため、モードによる diff コマンドの分岐は不要。

2. **サマリ + 影響クラスタ分割エージェントを起動する。** Task/Agent ツールでサブエージェントを起動し、以下の情報から (a) 変更内容のサマリ（`summary`。変更の意図・全体像・主要な変更点）と (b) **影響クラスタ分割案**（`clusters`）の2つを返させる。ステップ1と並列で実行してよい（ステップ1の結果に依存しない）。
   - **サマリエージェント入力**（モード別パラメータ表を参照）: 変更の意図・WHY を把握するための情報（PRタイトル・説明文・コミットメッセージ、または git log）。
   - `git diff $(jq -r '.diffArgs[]' "$CTX") $(jq -r '.excludeArgs.git[]' "$CTX")`: 差分テキスト（変更の具体的な内容を把握するため。レビュー対象外ファイルを除外した diff）。

   **返却物1: `summary`** — 変更サマリ。

   **返却物2: `clusters`** — ステップ3のエージェント4（クロスファイル整合性チェック）を並列化するための「影響クラスタ」の配列。クロスファイル整合性は「一緒に見ないと判定できないファイル群（変更されたシンボルとその参照/依存箇所）」の単位で閉じるため、この単位でレビューを分割すると検出力を保ったまま並列化できる。各クラスタは以下を持つ:
   - `id`: 連番（1始まり）。
   - `theme`: そのクラスタが何の変更のまとまりかを表す1行の説明。
   - `changedFiles`: このクラスタに属する**変更ファイル**（diff 内に現れるファイル）のパス配列。
   - `symbols`: このクラスタの整合性確認の焦点になる、変更された主要シンボル（メソッド/関数/クラス/定数/型/enum 等）の名前配列。
   - `contextHints`: 整合性確認のため参照を推奨する diff **外**ファイルのパス（呼び出し側・参照側・依存モジュールなど。分かる範囲でよく、網羅でなくてよい）。

   クラスタ分割の指針:
   - 変更を「一緒に見ないと整合性を判定できないファイル群」ごとにまとめる。呼び出し側と定義側、型と参照側、相互に依存する変更は**同一クラスタ**にする（分断すると整合性が見えなくなる）。
   - クラスタ数は**最大3**にキャップする。変更が小さく分けられない場合はクラスタ1つでよい（その場合エージェント4は1つになり、従来と等価）。
   - 各クラスタの `changedFiles` の合計が変更ファイルをおおむね覆うようにする。どのクラスタにも属さない孤立変更は、最も関連の近いクラスタに寄せる（それも無ければ独立クラスタにする）。
   - **`changedFiles` と `symbols` は、与えられた diff に現れるものだけを列挙する。diff に無いファイルを `changedFiles` に入れないこと**（diff は既にレビュー対象外ファイルを除外済みなので、除外ファイルは自然に対象外になる）。diff 外の参照先は `contextHints` にのみ記載する。

   このエージェントの出力は以下で消費する（宙に浮かせない）:
   1. **`clusters`**: ステップ3のエージェント4を各クラスタにつき1インスタンス並列起動するための入力。
   2. **`summary`**: ステップ7の「変更概要」の材料（**ステップ7の追加要素と完了後の動作** も参照）。

**並列サブエージェントの完了検知・待機（ステップ2・3・5の全並列エージェントに適用）:**
- 並列起動したサブエージェント（ステップ2のサマリ・ステップ3のレビューエージェント・ステップ5の検証エージェント）の完了は、**harness の完了通知（task-notification）を待つ**こと。
- **`ScheduleWakeup` による自己ポーリングや、サブエージェントの出力 JSONL／タスクファイルをタイムスタンプ・件数で覗き見して完了判定することを禁止する**（中断・ハングを誤検知し無限待機を招く）。
- サブエージェントが応答を返さず中断／異常終了した場合は、当該エージェントを **1回だけ再起動** する。再起動しても失敗し、かつその成果物が後続の必須入力でない場合はスキップして先へ進む。
- **エージェント4は複数インスタンスになりうる**（ステップ2の `clusters` の件数だけ並列起動する）。各インスタンスの完了は他のエージェントと同様に harness の完了通知で待つ。
- **サマリ + クラスタ分割エージェント（ステップ2）が失敗した場合、または `clusters` が空/不正だった場合の縮退動作**: エージェント4は**全 `changedFiles` を単一クラスタとみなして1インスタンスだけ起動**する（従来のエージェント4と等価。この単一クラスタには全変更ファイルを渡す）。著者意図情報の欠落時の扱いは **サマリ失敗時の縮退**（モード別パラメータ表）に従う。ステップ7の「変更概要」も同表に従って代替する。**サマリ／分割の失敗でレビュー全体を止めないこと。**

3. レビューエージェントを並列で起動し、変更内容を独立してレビューする。各エージェントは、課題の説明と指摘理由（例: 「CLAUDE.md準拠」「バグ」「REVIEW.md準拠」）を含む課題リストを返す。diff を取得するエージェント（3・4・5）には `git diff $(jq -r '.diffArgs[]' "$CTX") $(jq -r '.excludeArgs.git[]' "$CTX")`（レビュー対象外ファイルを除外した diff）を使わせること。各エージェントの起動タイミングは **ステップ3の起動タイミング**（モード別パラメータ表）に従う。**エージェント4はステップ2の `clusters` を入力に使うため、ステップ2の完了後にクラスタ数だけ並列起動する。** 各エージェントの役割は以下の通り:

   エージェント1, 2: プロジェクトルール準拠チェック（Sonnet）
   エージェント1はステップ1の `assignments[0].files`、エージェント2は `assignments[1].files` を担当し、並列でプロジェクトルール（CLAUDE.md および `.claude/rules/` 配下のルールファイル）への準拠を監査する。担当ファイルの振り分けはステップ1のスクリプトが決定済みのため、エージェント側で再分配しないこと。`assignments[1].files` が空の場合（全ファイルが1エージェントに収まる場合）はエージェント2を起動しないこと。各ファイルに適用すべきルールは `files[i].rules` に列挙済み（スコープ判定はスクリプトが完了している）。**あるファイルのレビューでは、そのファイルの `rules` に列挙されたルールファイルのみを適用すること。`rules` に含まれないルールでそのファイルを指摘しないこと。**

   エージェント3: バグ検出（Opus、エージェント4と並列）
   明らかなバグを探す。diffの内容のみに注目し、追加コンテキストの読み込みは行わない。重大なバグのみを指摘し、些細な指摘や誤検知の可能性が高いものは無視する。git diff外のコンテキストを参照しないと判断できない指摘は行わないこと。

   エージェント4: バグ検出／クロスファイル整合性チェック（Opus、**クラスタごとに複数インスタンスを並列起動**）
   ステップ2の `clusters` の各クラスタにつき Opus サブエージェントを1つ、メインエージェントが並列起動する（`clusters` が空/不正、またはステップ2が失敗した場合は、全 `changedFiles` を単一クラスタとみなして1インスタンスだけ起動する。上記「縮退動作」を参照）。各インスタンスには**担当クラスタの `theme` / `changedFiles` / `symbols` / `contextHints`** と、**著者意図情報**（モード別パラメータ表）を渡す（**個別サマリ本文は渡さない**。クラスタ自体が構造化された意図情報になっている）。各インスタンスは自クラスタの `changedFiles` に導入された問題（セキュリティ問題、ロジック誤り、クロスファイル整合性の崩れなど）を探す。エージェント3と異なり、変更コードの**周辺コンテキスト**まで読み込んでよい。具体的には以下の確認のためにdiff外のファイルを参照することを推奨する:

   - 変更したメソッド/関数のシグネチャ変更が、呼び出し側と整合しているか
   - 変更で導入/変更した定数・列挙値・型が、参照側の分岐ロジックと整合しているか
   - 変更したモジュール/クラスが、依存する他モジュール・テストと整合しているか
   - 変更ファイル単体では判断できない前提（暗黙のスコープ、共有状態、初期化順序など）が崩れていないか

   `contextHints` は整合性確認の**起点であって上限ではない**。上記の確認に必要なら、`contextHints` に無いファイルも追加で読んでよい（意味的なクラスタ分割は網羅的ではないため、LLM 側の探索で補う）。

   ただし以下は守ること:
   - 確信が持てない指摘は行わない（誤検知はレビュアーの信頼を損なう）
   - diff外のコードに既に存在していた問題（**既存問題の基準**（モード別パラメータ表）より前から存在する問題）は指摘しない
   - **レビュー対象外ファイル（生成物・ミニファイ・バイナリ等。`contextHints` に混じっていても）そのものを指摘対象にしない。** 参照はしてよいが、そこの問題は指摘しない。
   - 指摘時は、関連するdiff外ファイルのパスと該当箇所も明示する
   - 自クラスタの `changedFiles` に導入された問題のみを指摘する（他クラスタの変更は担当外。重複はステップ4で統合される）

   エージェント5: REVIEW.md準拠チェック（Sonnet、エージェント1〜4と並列）
   ルート直下の `REVIEW.md` に記載されたレビュー観点への新規違反を監査する。観点ファイルのロードは以下のルールに従うこと:

   - 「常時適用される観点」セクションで `@` インポートされている観点ファイルは必ず読み込む。
   - 「条件付き観点」セクションは、まずインデックス（観点名・観点ファイルのパス・適用対象の説明）のみを読む。各観点について、変更内容（変更ファイルのパスとdiff）が「適用対象」に該当するかを判断する。**該当する観点のみ**、観点ファイル本体を読み込んでレビューに使用する。該当しない観点の本体ファイルは読み込まないこと。
   - 適用するか迷う場合はロードする側に倒してよいが、明らかに無関係な観点はロードしないこと（例: ドキュメントだけの変更で金額計算観点をロードする必要はない）。

   注: あるファイルに対するルールの適用可否（ディレクトリスコープ・ファイル種別など）は REVIEW.md および観点ファイル側の記述に従い、適用範囲外のルールで指摘しないこと。指摘時は該当ルールの引用元へのリンクを必ず含める。

   **重要: 高シグナルな指摘のみを対象とする。** 以下に該当する指摘のみを行うこと:
   - コードがコンパイル/パースに失敗する（構文エラー、型エラー、import漏れ、未定義参照など)
   - 入力に関わらず明らかに誤った結果を返す（明確なロジックエラー）
   - 該当ルールを引用できる、明白かつ明確なプロジェクトルール（CLAUDE.md または `.claude/rules/`）違反

   以下は指摘しないこと:
   - コードスタイルや品質に関する懸念
   - 特定の入力や状態に依存する潜在的な問題
   - 主観的な提案や改善案

   実際に問題かどうか確信が持てない場合は指摘しないこと。誤検知はレビュアーの信頼を損ない、時間を浪費させる。

   各エージェントに**著者意図情報**（モード別パラメータ表）を渡す。エージェント4にはさらに担当クラスタ（`theme` / `changedFiles` / `symbols` / `contextHints`）を渡す（`summary` 本文は渡さない。クラスタが構造化された意図情報を担う。ただし**著者意図情報**が `summary` そのものであるモードでは、エージェント4への著者意図情報として `summary` を渡してよい）。エージェント1・2・3・5 に `clusters` は渡さない（ルール準拠系・REVIEW.md準拠系は担当ファイルへの局所的な違反照合であり全体意図は判断軸に入らないため、また diff限定のエージェント3は役割上追加コンテキストを持たないため）。

4. ステップ3で集約した全課題について、重複を統合する（**エージェント4は複数インスタンス（クラスタ並列）になりうるため、インスタンス間で同一箇所を別々に指摘する重複も統合対象**）。**同一ファイル（`path`）の同一箇所・同一趣旨の指摘を1件に統合する**（例: エージェント3と4が同じバグを別々に検出した場合、複数のエージェント4インスタンスが同一箇所を検出した場合、ルール系とバグ系が同一箇所を別観点で指摘した場合）。統合はメインエージェントが機械的に行い、対象コード片の重なりと指摘趣旨の一致で判定する（この時点で行番号は未確定のため、指摘対象コード片・記述の重なりで近接を判断する。別ファイル・別趣旨のものは統合しない）。**統合後の課題には由来エージェント種別（バグ系: 3・4由来 / ルール系: 1・2・5由来）を保持する。バグ系とルール系が混在する場合はバグ系として扱う**（次ステップの検証でOpusを使うため）。以降のステップには、統合後の課題のみを渡す。

5. ステップ4で統合された各課題について、検証用のサブエージェントを並列起動する。各サブエージェントには、**著者意図情報**（モード別パラメータ表）と課題の概要を渡す。サブエージェントの役割は、提示された課題が高い確度で実際の問題であるかを検証すること。例えば「変数が未定義」と指摘された場合、コード上で実際にそれが正しいかを確認する。プロジェクトルール違反（エージェント1, 2由来。CLAUDE.md および `.claude/rules/`）の場合、適用スコープはステップ1のスクリプトが `files[i].rules` として確定済みのため、その範囲内で実際に違反しているかのみを検証する（`paths` 一致の再判定は不要）。REVIEW.md 違反（エージェント5由来）の場合は、該当観点がそのファイルに適用される対象か、かつ実際に違反しているかを検証する。バグ・ロジック系（エージェント3, 4由来）の検証にはOpusサブエージェントを、プロジェクトルール違反（エージェント1, 2由来）およびREVIEW.md違反（エージェント5由来）の検証にはSonnetエージェントを使用する。

6. ステップ5で検証されなかった課題は除外する。これにより最終的な高シグナル課題リストが得られる。

7. レビュー結果のサマリをターミナルに出力する:
   - **ステップ7の追加要素と完了後の動作**（モード別パラメータ表）に「冒頭に『変更概要』を載せる」旨が指定されている場合は、まず冒頭にステップ2のサマリエージェント出力を「変更概要」として簡潔に載せる（サマリの縮退時は **サマリ失敗時の縮退**（モード別パラメータ表）に従って代替する）。
